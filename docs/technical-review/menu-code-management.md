# 메뉴 계층과 공통 기준 정보를 안전하게 운영

사용자 메뉴와 공통 코드는 화면에 표시할 문자열만 저장하는 데이터가 아니다. 메뉴의 부모 관계가 깨지면 탐색 구조를 만들 수 없고, 공통 코드가 중복되거나 비활성 값과 섞이면 두 서비스가 같은 상태를 다르게 해석할 수 있다. 현재 구현은 계층 규칙과 기준값 검증을 관리자 ServiceImpl에서 먼저 적용한다.

## 사용자 메뉴 계층

`UserMenuServiceImpl`은 메뉴 등록과 수정에서 상위 메뉴를 조회해 현재 단계를 계산한다. 다음 조건은 저장 전에 거부한다.

- 자기 자신을 상위 메뉴로 선택한 경우
- 자신의 하위 메뉴를 새 상위 메뉴로 선택해 순환이 생기는 경우
- 현재 메뉴와 하위 트리를 이동했을 때 최대 3단계를 넘는 경우
- 존재하지 않는 상위 메뉴를 선택한 경우

삭제 시에는 하위 메뉴 수를 먼저 확인한다. 자식이 남아 있는 부모를 삭제하지 않기 때문에 트리가 끊긴 채 저장되는 상황을 막는다. 숨김 메뉴는 정렬 대상에서 제외하고, 노출 메뉴에는 유효한 정렬 순서를 적용한다.

## 공통 코드 관리

공통 코드는 그룹과 세부 값으로 나뉜다. `CodeManageService`는 그룹과 세부 코드의 필수값, 중복 여부, 사용 상태와 관리 정보를 검증한다. 화면이 임의의 상태 문자열을 저장하지 않고, 사용자·알림·신고 등 여러 기능이 공유할 수 있는 기준값을 한곳에서 관리하는 구조다.

공통 코드를 데이터로 관리하면 앱을 다시 빌드하지 않고 표시명과 사용 여부를 바꿀 수 있다. 반면 코드의 의미나 식별값을 바꾸면 두 서비스의 분기와 기존 데이터가 함께 영향을 받는다. 따라서 단순 문구 수정과 업무 의미 변경을 구분해야 한다.

## 사용자 서비스 적용

사용자 서비스는 활성 사용자 메뉴를 조회해 계층 구조를 만들고, 공통 코드를 상태명과 카테고리 같은 기준 정보로 사용한다. 관리자 프로젝트는 기준 정보를 편집하지만, 사용자 화면에 어떻게 배치할지는 사용자 서비스가 결정한다. 두 프로젝트의 책임을 분리하면서도 같은 데이터 계약을 공유하는 방식이다.

## 한계와 개선점

메뉴와 공통 코드는 공통 데이터베이스에 결합되어 있다. 작은 팀에서는 즉시 반영과 단순한 운영이 장점이지만, 각 서비스가 독립적으로 배포되고 변경 빈도가 높아지면 스키마와 코드 의미의 동시 변경 비용이 커진다. 변경 이력과 호환 기간이 필요해지면 버전이 있는 API 또는 이벤트 계약으로 분리하는 방안을 검토할 수 있다.
